# FMI 2 behaviour

A fmugen FMU is a UniFMU FMU (FMI 2.0 Co-Simulation). The native UniFMU library in `binaries/` starts a Python process (`resources/main.py`), which forwards each FMI call to the adapter in `resources/model.py`. The adapter is generated by fmugen and is the same for every model. It reads `resources/interface.json` to find out how each FMU variable maps onto your code.

This page describes what the adapter does for each FMI call, and which parts of FMI 2 are not available.

---

## Life cycle

```
fmi2Instantiate ─► [set parameters, inputs, state starts] ─► fmi2SetupExperiment
   ─► fmi2EnterInitializationMode ─► [set ...] ─► fmi2ExitInitializationMode
   ─► loop: [set inputs / tunable parameters] ─► fmi2DoStep(t, h) ─► [get outputs]
   ─► fmi2Terminate ─► fmi2FreeInstance
```

| FMI call | What the adapter does |
|---|---|
| `fmi2Instantiate` | Adds the model's directories (and `resources/site`) to `sys.path`, imports the entry, and sets every variable to its start value. A class is **not** constructed yet, because parameters may still change. |
| `fmi2SetupExperiment(start, stop, tol)` | Stores them; the FMU's time becomes `start`. |
| `fmi2EnterInitializationMode` | Nothing to do. |
| `fmi2ExitInitializationMode` | **Class:** constructs the object with the parameters and `[model.constants]`, then writes `attr:`-bound variables onto it. **Function** (or `init_call = true`): calls the model once at the start time to compute initial outputs. States are not advanced. Then reads outputs, locals and calculated parameters; attributes that don't exist yet keep their start values. |
| `fmi2DoStep(t, h, …)` | Rejects `h` if `fixed_step` is set and `h` differs. Writes `attr:` inputs, then calls the function or step method with the inputs, parameters bound to `arg:`, states, time arguments and `call_constants`. Reads outputs, locals and calculated parameters, then replaces each state with its `next` value. The FMU's time becomes `t + h`. |
| `fmi2Set{Real,Integer,Boolean,String}` | See [Setting variables](#setting-variables). |
| `fmi2Get{Real,Integer,Boolean,String}` | Returns current values. An Enumeration is read with `fmi2GetInteger`. |
| `fmi2Terminate` | Calls `[model] terminate` on the object, if set. |
| `fmi2Reset` | Discards the object, and restores start values and the start time. The next initialization constructs a fresh object. |
| `fmi2GetFMUstate` / `fmi2SetFMUstate`, `fmi2SerializeFMUstate` / `fmi2DeSerializeFMUstate` | Pickles and unpickles all variable values, the model object (deep copy) and the time. This is what lets an importer roll back a step. |
| `fmi2SetDebugLogging` | Turns forwarding of the model's log records on or off. |
| `fmi2FreeInstance` | The Python process exits. |

**Step semantics:** `doStep(t, h)` takes the inputs at `t` and produces outputs at `t + h`.

**Errors:** any exception raised by your code makes the call return `fmi2Error`. The traceback is logged under `logStatusError`. The importer decides what happens next; most stop the simulation.

## Setting variables

| Variable | Before initialization is done | After (during stepping) |
|---|---|---|
| input | ✓ | ✓, used by the next step |
| parameter, `fixed` | ✓ | ✗ `fmi2Error`. FMI 2 forbids changing fixed parameters after initialization. |
| parameter, `tunable` | ✓ | ✓. For classes the value is also written to the object attribute (`attr`), and calculated parameters are re-read. |
| state (`local`, `initial="exact"`) | ✓ sets its initial value | ✗ |
| output, local, calculated parameter | ✗ | ✗ |

"Before initialization is done" covers both before and during initialization mode.

---

## FMU state

`canGetAndSetFMUstate` and `canSerializeFMUstate` are `true` when the model object can be pickled. `fmugen build` checks this by running the packaged model once and saving its state. If that fails (the object holds a file handle, generator, socket, …), both flags are written as `false`.

Restoring a state restores the whole Python object, so classes that keep internal state (integrators, filters, controllers) roll back correctly too.

## Logging

Your code uses the standard `logging` module. While the adapter runs your code, a handler forwards every record to the importer through UniFMU:

| Record level | Status | Category |
|---|---|---|
| ≥ `ERROR` | `fmi2Error` | `logStatusError` |
| `WARNING` | `fmi2Warning` | `logStatusWarning` |
| below | `fmi2OK` | `logAll` |

- **When forwarding happens:** only during an FMI call. UniFMU can only carry a log message while it is processing a command, so records from background threads aren't forwarded.
- **Filtering:** UniFMU filters categories according to the importer's settings. `modelDescription.xml` declares the standard categories plus `logUnifmuMessages`.

## Capabilities written to `modelDescription.xml`

| Attribute | Value |
|---|---|
| `needsExecutionTool` | `true`: a Python interpreter is needed (see [packaging.md](packaging.md#runtime-python)) |
| `canHandleVariableCommunicationStepSize` | `true`, or `false` with `[experiment] fixed_step` |
| `canGetAndSetFMUstate`, `canSerializeFMUstate` | from the build probe (see above) |
| `canNotUseMemoryManagementFunctions` | `true` |
| `canInterpolateInputs`, `maxOutputDerivativeOrder`, `canRunAsynchronuously`, `providesDirectionalDerivative` | not declared, so they take their FMI defaults: `false` / `0` |

## Unsupported FMI 2 functions

The UniFMU 0.14 Python backend (`resources/backend.py`) has no handler for the following functions. fmugen declares them as unsupported in `modelDescription.xml`, so a compliant importer never calls them. None of them is required by FMI 2, and none of them is useful for ordinary Python models:

| Function | What it is for | Why it isn't needed here |
|---|---|---|
| `fmi2CancelStep` | Abort a `doStep` that is still running asynchronously (one that returned `fmi2Pending`) | `doStep` always finishes before returning, so there is never anything to cancel. |
| `fmi2GetDirectionalDerivative` | Give the importer Jacobians (∂outputs/∂inputs) for Model Exchange solvers or co-simulation algorithms that solve algebraic loops between FMUs | Your model would have to compute derivatives, which ordinary Python models don't. Rarely used in Co-Simulation. |
| `fmi2SetRealInputDerivatives` | Pass input slopes so the FMU can interpolate inputs within a step | An accuracy refinement for large steps. Importers hold inputs constant over a step unless `canInterpolateInputs` is true. |
| `fmi2GetRealOutputDerivatives` | Report output slopes so the importer can extrapolate | Same as above, and only requested when `maxOutputDerivativeOrder` > 0. |

> **Caveat:** if a non-compliant importer calls one of these anyway, the Python backend stops with "unrecognized command", and the simulation fails rather than getting `fmi2Error` back.

## Out of scope

UniFMU can do more than fmugen currently targets:

- **FMI 3.0:** `unifmu generate python <dir> fmi3`, with more types, clocks and events. fmugen's interface spec is independent of the FMI version, so an FMI 3 writer and adapter can be added later.
- **Distributed FMUs:** `unifmu generate-distributed`, where the FMU is a proxy and the model runs on another machine.
- **Other backends:** C# and Java.
- **Model Exchange:** UniFMU's FMUs are Co-Simulation only.

See the [UniFMU repository](https://github.com/INTO-CPS-Association/unifmu) for these.
